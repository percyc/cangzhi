# 藏知关键技术决策

本文件记录技术选择及重新评估条件，避免开发过程中反复更换方向。早期里程碑决策会
保留作为演进记录；标记“已被后续决策取代”的章节不是当前能力说明，当前实现以
[技术架构](ARCHITECTURE.md)为准。

## ADR-001：首版采用模块化单体

**决定**：Web、API 和 Worker 进程分开，但共用一个仓库、一个数据库和一套领域模型。

**原因**：个人版的数据量和并发不需要微服务；独立 Worker 已能隔离耗时解析任务。

**重新评估条件**：团队版出现不同扩缩容需求，或单类任务持续占据主要资源。

## ADR-002：PostgreSQL 同时承载元数据、全文和向量

**决定**：首版使用 PostgreSQL `tsvector` 与 pgvector，不部署独立 Elasticsearch/OpenSearch 和向量数据库。

**原因**：减少组件和备份复杂度，同时足以支撑个人知识库规模。

**重新评估条件**：文档达到数十万级、复杂全文功能成为瓶颈，或需要多租户独立索引。

## ADR-003：原文与结构树是事实源

**决定**：原文件、网页快照和结构节点长期保存；摘要、分类、切片、Embedding 和图谱都是可重建派生物。

**原因**：模型和解析器会持续升级，必须允许重新处理且不损失来源证据。

## ADR-004：结构优先、确定性切片

**决定**：优先依照章节、段落、列表、表格和条款边界切片；当前主路径不让 LLM
直接决定切片边界。只有黄金评测证明特定领域确有收益时，才可把 LLM 作为可版本化、
可回退的辅助步骤。

**原因**：全量 LLM 切片成本高、边界不稳定，也不利于幂等和用户编辑。

## ADR-005：采用父子检索单元

**决定**：较小 child chunk 用于召回，较大 parent node 用于回答上下文。

**原因**：兼顾精确召回与完整语境，并能保持章节路径和原文位置。

## ADR-006：默认混合检索

**决定**：全文与向量并行召回，通过 RRF 融合，Reranker 作为可选增强。

**原因**：精确术语、条号和专有名词依赖全文检索；改写和概念相近问题依赖向量检索。

## ADR-007：后台任务先用数据库队列

**决定**：首版通过 `processing_jobs` 表、锁和独立 Worker 承载任务，不立刻引入 Redis。

**原因**：减少个人部署组件，任务量有限且需要持久、可审计状态。

**重新评估条件**：任务吞吐、定时调度或多 Worker 竞争使数据库队列维护成本明显增加。

## ADR-008：模型 Provider 可替换

**决定**：解析理解、分类、Embedding、Rerank 和回答使用独立任务接口，不在领域代码中绑定具体供应商。

**原因**：支持云模型、本地 Ollama、隐私需求和成本优化，并允许不同任务选用不同模型。

## ADR-009：首版单用户但不写死用户边界

**决定**：UI 和数据库约束只支持一个管理员，不实现团队权限矩阵。当前知识表不虚构
尚未使用的 `owner_id/workspace_id`；进入多用户阶段时通过明确迁移增加所有权边界。

**原因**：避免首版权限系统拖慢交付，同时保留以后迁移空间。

## ADR-010：知识图谱不是首版基础依赖

**决定**：首版仅保存实体提取结果和必要关系，不运行全量 GraphRAG。

**原因**：普通个人资料的主要问题是可靠采集、分类和召回；全量图谱成本高且在语料尚小时收益不确定。

**重新评估条件**：出现大量跨文档实体关系问题，且黄金评测证明混合检索无法满足。

## ADR-011：M3 检索先做 FTS 与结构切片，向量召回延后

**状态**：已被 ADR-015、ADR-016 和当前混合检索实现取代，保留为里程碑记录。

**决定**：M3 第一小版只交付 PostgreSQL 全文索引（`tsvector` + GIN）以及
基于 `structured_content` 的父子切片；embedding、向量召回、RRF 融合和带
引用问答保留到 M3 后续。

**原因**：在拥有 50 份以内个人资料时，关键词 + 标题 + heading_path 路径
检索已经能命中绝大多数真实问题；过早引入向量会同时拖慢里程碑验收和
增加外部依赖（模型服务、pgvector 资源占用）。让 FTS 先稳定后再叠加
向量，有利于按 ADR-006 的“混合检索”策略分阶段做评测。

**重新评估条件**：M3 黄金集上 FTS Top 5 命中率低于 80%，或资料数 / 跨
文档问题显著上升，导致关键词召回不足。

## ADR-013：M3-3 引入单用户认证与网页模型设置，使用 scrypt 会话、Fernet 加密与数据库唯一约束

**决定**：M3-3 在同一数据库中新增 ``admins``、``auth_sessions``
和 ``ai_runtime_configs`` 三张表。管理员密码使用 scrypt（参数
N=2^14, r=8, p=1）哈希并以自描述 ``scrypt$N=...,r=...,p=...$salt$hash``
格式存储；API key 使用 Fernet 加密落库，主密钥先看
``CANGZHI_SECRET_KEY`` 环境变量，否则在共享 storage 中以
0o600 权限生成 ``.secret_key``。会话 token 为 32 字节 URL-safe
随机串，HttpOnly + SameSite=Lax Cookie，12 小时 TTL，数据库只
存 SHA-256。``/login`` 在进程内按客户端 IP+账户限流，``/setup``
按客户端 IP 限流。
单管理员与单 AI 配置分别通过 ``singleton_key`` 唯一约束在
数据库层强制，即使应用层检查被绕过，重复 ``setup`` 或并发
插入也只会留下第一行。AI provider 加载新增
``build_provider_from_db``（API 路径）和
``build_provider_from_session``（Worker 路径），web 配置始终覆
盖 ``.env``，``/api/settings/ai`` GET 响应只回显 ``has_api_key``
布尔值与配置字段，不返回密钥或密钥提示。

**原因**：首版只在局域网内使用，但要支持公网部署和共享服务器
就必须先有最基础的访问控制。scrypt 在 stdlib 中可用（不需要
第三方 C 扩展），参数比 bcrypt 更现代。Fernet 提供认证加密，
避免单独写 MAC；主密钥放在 storage 共享卷里，API 和 Worker 都
能读取，进程内只缓存一次。``singleton_key`` 唯一约束是廉价的
纵深防御：应用层已经做了 ``count == 0`` 检查，数据库层再加一
道。Next.js ``proxy.ts``（原 ``middleware.ts``）只做浏览器引导，
API 是最终安全边界，这样可以避免 middleware 重复查询和绕过
``dependency_overrides``。

**重新评估条件**：出现多账户/团队空间需求时升级为完整的用户
表与权限矩阵；接入云 KMS 后主密钥改用 KMS；如需 SSO/OAuth
则换成 JWT 或 OIDC。

## ADR-012：M3-2 问答只做单轮 FTS 检索，不引入向量与对话记忆

**状态**：FTS-only 部分已被 ADR-016 取代；“默认不把历史问答注入模型”继续有效，
问答审计记录由 ADR-017 的无状态取证与持久记录方案补充。

**决定**：M3-2 在不破坏 ADR-011 的前提下交付首版单轮带引用问答：
证据来自 `document_chunks` 的 PostgreSQL FTS 与 SQLite `LIKE` 召回；
模型输出受 `AnswerResult` 与 `validate_against_evidence` 严格约束；
不保存会话历史、不引入 embedding、不做 RRF。

**原因**：个人知识库首版必须能用自然语言提问并拿到可验证的引用，
但黄金评测集尚未建立，向量召回会同时拉高复杂度与外部依赖。在
FTS 之上先稳定“提问-召回-回答-引用”闭环，能更快暴露真实的问答
质量问题（截断、片段过长、引用造假、证据不足），再决定向量与
多轮的优先级。

**重新评估条件**：M3 黄金集上 FTS Top 5 命中率低于 80%、跨文档
问题占比明显上升、且问答错误主要由召回能力不足（而非生成或
引用校验）造成；同时 ADR-011 的重新评估条件也被触发。

## ADR-014：M3-4 确定性文档类型检测，不依赖 LLM 逐个判断

**决定**：M3-4 新增确定性文档类型检测模块，仅基于结构统计和关键词
匹配输出文档类型；不调用 LLM 判断每个文档的边界和类型；检测结果写入
元数据供分块和后续处理使用，类型决定分块参数但不影响原始结构保存。

支持输出类型：`general/legal/contract/paper/meeting/code/table`。
低置信度必须降级为 `general`，保证召回稳定。不同类型使用不同分块参数：
- `general`: 默认参数，保持当前行为
- `code/table`: 更大块参数，尽量保持单个代码块/表格完整
- `legal/contract/paper/meeting`: 首版只做识别和记录，分块使用默认参数

**原因**：
1. 文档类型判断在结构解析后就有足够特征（扩展名、块比例、关键词），
   不需要调用 LLM，降低成本并保证结果确定，满足幂等要求。
2. 不同类型确实需要不同分块策略：代码/表格需要更大块，否则拆分后语义不完整。
3. 先实现确定性规则基线，未来可以在规则不置信的地方引入 LLM 辅助判断，
   不需要一开始就全量 LLM。
4. 父片段继续保存完整语义章节，不设置容易误导的字符上限；用于召回的
   子片段严格受类型配置约束，回答时仍可追溯完整父章节。

**重新评估条件**：确定性规则准确率低于 70%，大量文档被错误分类导致
分块质量退化；或者用户希望自定义文档类型和特定分块策略，那时再引入
LLM 辅助和用户可编辑配置。

## ADR-015：向量配置与索引版本分离，兼容检测后再切换

**决定**：

1. Embedding 使用独立于聊天模型的 provider、base URL、API key、模型名和
   超时配置。更换聊天渠道不影响向量索引，更换向量渠道也不影响分类和问答。
2. “候选配置”“正在构建的索引”“当前服务索引”是三个不同状态。保存或测试
   候选配置不会覆盖当前服务索引，也不会让检索中断。
3. 每套向量空间保存为一个 `embedding_profile`，记录 provider、模型名、
   维度、距离算法、固定 canary 文本的向量指纹、配置指纹、状态和构建进度；
   `chunk_embeddings` 通过 profile_id 关联具体空间。
4. 兼容性不能只凭模型名或维度判断。候选配置测试时，对多条固定 canary
   文本生成向量，并与当前 profile 的 canary 向量逐条计算余弦相似度：
   - 配置指纹完全相同：无需重建。
   - 仅地址、渠道或密钥变化，维度相同且全部 canary 相似度不低于 0.999：
     标记为“高度兼容”，允许用户选择免重建切换。
   - 模型名变化、维度变化、缺少历史 canary、相似度低于阈值或测试异常：
     默认必须重建。
   - 维度相同但没有通过 canary，不得宣称兼容。
5. 重建采用蓝绿方式：旧 profile 继续检索，新 profile 后台批量构建；只有
   当前 child chunks 覆盖率达到 100% 且无失败任务时才允许原子激活。失败时
   保留旧 profile，候选 profile 可重试或删除；激活后仍保留上一版本用于回滚。
6. 文档新增或内容变化时，只为当前激活 profile 自动补向量；若另一个 profile
   正在构建，也同时补入构建目标。chunk 的 content_hash 用于幂等更新。
7. PostgreSQL 每个 profile 的维度必须固定。首版用 pgvector 精确余弦检索；
   profile 激活且语料量达到阈值后再按固定维度建立 HNSW。不同维度不混放在
   同一个有索引的向量列中。SQLite 测试只验证状态机和数据契约，不承担性能检索。

**状态机**：

`draft -> tested -> building -> ready -> active -> retired`，失败进入 `failed`；
只有 `ready` 可以激活，只有 `active/retired` 可以作为回滚目标。系统始终最多
一个 active profile。

**安全与运行规则**：

- API key 继续加密落库，接口只返回 `has_api_key`；测试错误不返回上游正文。
- 候选配置测试最多发送三条短 canary，不读取用户文档。
- 批量任务按小批次执行，遵循数据库队列的重试、退避和幂等约束。
- 不允许在构建未完成时“强制激活”；管理员可取消构建，但旧索引不受影响。
- “免重建”是显式用户选择，并显示检测依据；系统不会仅因名称相同自动决定。

**原因**：向量空间由模型权重、版本、供应商实现、归一化和输入前缀共同决定。
同名模型在不同渠道可能兼容，也可能发生静默漂移；直接覆盖旧向量会造成查询
向量与文档向量不在同一空间。版本化蓝绿索引能在支持随时换模型的同时保持检索
可用、结果可解释且可回滚。

**重新评估条件**：单库向量超过 10 万条、多 profile 长期并存导致存储成本明显
上升，或需要多租户隔离时，评估分区表、专用向量数据库和分布式任务队列。

## ADR-016：active profile 查询向量与 RRF 混合召回

**决定**：

1. 每次搜索或问答只为用户查询生成一次向量，并且只查询
   `ai_runtime_configs.active_embedding_profile_id` 对应的向量空间。
2. 关键词与向量各自独立排序，以 chunk id 为稳定标识，通过
   Reciprocal Rank Fusion（`k=60`）融合，不直接比较两种不可比的原始分数。
3. 元数据过滤在两路召回 SQL 中使用同一套条件；仅查询当前版本的 child chunk，
   保持结果可追溯到文档、版本和原文位置。
4. 查询向量生成、配置解析或向量 SQL 失败时，不中断请求，自动退回关键词召回；
   API 返回结构化 `retrieval` 状态，页面向用户显示实际模式和脱敏后的降级原因。
5. 首版小规模个人库使用 pgvector 精确余弦距离；达到性能阈值后再为固定维度的
   active profile 建立近似索引，不提前增加索引生命周期复杂度。

**原因**：全文搜索擅长条号、专名和精确术语，向量检索擅长改写与概念近似。
RRF 不依赖两路分数校准，适合作为稳定、可解释的默认融合基线。把降级状态暴露
给页面，可以避免向量服务故障被静默掩盖，同时保证个人知识库始终可搜索。

**重新评估条件**：黄金问题集证明加权 RRF、Reranker 或查询改写能显著提高
Top 5 命中率；或 active profile 超过 10 万个切片导致精确余弦查询延迟不可接受。

## ADR-018：WebDAV 远端删除采用延迟确认和可恢复处理

**决定**：

1. WebDAV 是只读知识来源，不对远端执行删除、改名或覆盖。
2. 一次成功扫描未看到原有文件时，只进入 `suspected_missing`；至少连续两次
   成功扫描且首次缺失超过 24 小时，才确认为 `missing`。扫描失败不累计确认。
3. 默认策略是将关联知识移入回收站，保留原文、版本、切片和向量，不自动永久删除。
4. 远端文件重新出现时，因 `remote_missing` 回收的知识自动恢复并进入更新流程；
   用户主动删除、连接器删除和永久删除不使用这一自动恢复规则。
5. 用户可以将已确认缺失的资料标记为本地知识快照，恢复到知识库并停止随远端缺失
   自动回收。连接器也可以配置为始终保留本地快照。
6. 文件因扩展名或忽略规则变化而不再属于扫描范围时，不视为远端删除。

**原因**：远端临时故障、权限变化和不完整目录响应不能触发批量知识删除；另一方面，
完全忽略远端删除又会让 WebDAV 失去来源一致性。延迟确认、回收站和快照保留把
“来源事实”“本地知识可用性”“不可逆删除”拆成三个独立决定。

**重新评估条件**：引入可靠事件订阅、远端版本历史或双向同步时，重新评估确认窗口
和冲突处理；在此之前不允许跳过回收站或自动永久清理。

## ADR-019：先交付单管理员多工作空间，不直接扩展为多用户系统

**决定**：

1. 工作空间是个人知识上下文和数据隔离边界，不承担账号、成员或角色语义。
2. 新增不可归档的 `default` 空间；升级前数据全部回填到该空间，未提供选择的旧客户端
   继续访问默认空间。
3. 文档、分类、标签、知识范围、WebDAV 来源、远端排除记录和问答会话直接归属空间；
   版本、切片、数据集和证据通过所属文档继承边界。
4. 浏览器使用 Cookie；REST、CLI、MCP 和 Skill 使用稳定请求头选择空间。未知空间
   拒绝访问，归档空间只保留管理和恢复能力。
5. 对话模型、Embedding 配置及 Profile、管理员、令牌、备份和系统任务配置暂时全局共享。
6. Worker 每次根据任务所属文档重新绑定空间，不能沿用上一任务的空间上下文。

**原因**：当前核心用户仍是一个人，但工作、家庭和专题资料需要明确隔离。直接做多用户
会同时引入邀请、成员、角色、资源授权、共享、审计和密钥归属，显著扩大安全面，却不能
更快解决个人资料混杂问题。先把空间边界建稳，未来多用户只需在空间之上增加成员关系和
授权，而不必重做知识数据模型。

**重新评估条件**：出现真实的第二位独立使用者、空间共享或不同管理员权限需求时，新增
`users`、`workspace_memberships`、角色与 PAT 空间授权；在此之前不把空间伪装成用户。

## ADR-020：关系数据库先作为只读快照来源，不开放任意 SQL

**决定**：

1. 首版支持 PostgreSQL/MySQL；连接配置加密保存并归属工作空间。
2. 用户只能从服务端目录发现的 Schema、表和视图中选择导入。系统按驱动安全引用
   标识符，并强制只读事务、连接超时、语句超时和 10 万行上限。
3. 每次导入形成藏知本地快照，进入既有 `KnowledgeDataset → Parquet → DuckDB` 执行层；
   API、MCP 和 Skill 继续使用受控查询计划，不把来源库凭据或 SQL 能力暴露给外部 Agent。
4. 同一来源表重导入沿用稳定文档、增加文档版本并原子替换数据集。数据库提交失败时
   删除新产物；新快照提交成功后才清理旧 Parquet。
5. 首版不执行自定义 SQL，不直接恢复 `.sql` dump，也不做双向写入、CDC 或定时同步。

**原因**：藏知的职责是保存可验证的知识快照并提供统一取证，不是数据库客户端或 ETL
编排器。目录选择覆盖多数个人分析场景，又能把 SQL 注入、长查询、写入远端、外部模型
误操作和凭据泄露限制在清晰边界之外。

**重新评估条件**：真实数据超过整表快照上限或需要持续更新时，优先增加可视化列/筛选
选择、后台导入、增量键和调度；仅在 SQL dump 有明确通用解析需求时增加“解析但不执行”
的隔离导入器。

## ADR-021：外部系统使用工作空间令牌与文档 Scope Key

**决定**：PAT 可选绑定一个工作空间；外部系统用独立 `document_scope_keys` 关联表为
文档维护不透明分组标识。查询的 `document_selection` 将多个 Scope Key 命中文档与多个
明确 Document ID 取并集，再与 KnowledgeScope 和元数据筛选取交集；不传选择时访问整个
空间。Scope Key 不承担用户身份、角色或组织权限语义。文件上传和范围管理使用独立
`documents:write`，MCP 保持读取工具。

**原因**：为外部系统和 Agent 提供可组合的文档集合，同时避免把单用户知识中枢扩展成
复杂权限平台。规范化关联表和 SQL 下推保证大规模过滤与统一相关性排序。

完整安全边界和接口见 [ADR-021](ADR-021-external-client-access.md) 与
[外部系统接入](EXTERNAL_CLIENT_ACCESS.md)。

## ADR-023：受约束 AI 切片候选

**决定**：模型只提议原文块分组终点，程序保证顺序与完整覆盖。先提供管理员主动
生成的候选比较，不改写正文，不替换现有索引。原子启用、旧引用保留及真实黄金集
仍是启用门槛。参见 [ADR-023](ADR-023-assisted-chunking-candidates.md)。

## ADR-024：可选 AI 知识增强

保留基础 AI 整理，将分层理解、证据图谱和替代切片作为独立可选增强。切片单代
生效、补充产物并存、范围约束共享、读取不调用模型。见 [ADR-024](ADR-024-optional-knowledge-enhancement.md)。
