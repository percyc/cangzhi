# 藏知关键技术决策

本文件记录当前默认选择及重新评估条件，避免开发过程中反复更换方向。

## ADR-001：首版采用模块化单体

**决定**：Web、API 和 Worker 进程分开，但共用一个仓库、一个数据库和一套领域模型。

**原因**：个人版的数据量和并发不需要微服务；独立 Worker 已能隔离耗时解析任务。

**重新评估条件**：团队版出现不同扩缩容需求，或单类任务持续占据主要资源。

## ADR-002：PostgreSQL 同时承载元数据、全文和向量

**决定**：首版使用 PostgreSQL `tsvector` 与 pgvector，不部署独立 Elasticsearch/OpenSearch 和向量数据库。

**原因**：减少组件和备份复杂度，同时足以支撑个人知识库规模。

**重新评估条件**：文档达到数十万级、复杂全文功能成为瓶颈，或需要多租户独立索引。

## ADR-003：原文与结构树是事实源

**决定**：原文件、网页快照和结构节点长期保存；摘要、分类、切片、Embedding 和图谱都是可重建派生物。

**原因**：模型和解析器会持续升级，必须允许重新处理且不损失来源证据。

## ADR-004：结构优先、LLM 辅助切片

**决定**：优先依照章节、段落、列表、表格和条款边界切片；LLM 只用于结构不清或领域复杂的内容。

**原因**：全量 LLM 切片成本高、边界不稳定，也不利于幂等和用户编辑。

## ADR-005：采用父子检索单元

**决定**：较小 child chunk 用于召回，较大 parent node 用于回答上下文。

**原因**：兼顾精确召回与完整语境，并能保持章节路径和原文位置。

## ADR-006：默认混合检索

**决定**：全文与向量并行召回，通过 RRF 融合，Reranker 作为可选增强。

**原因**：精确术语、条号和专有名词依赖全文检索；改写和概念相近问题依赖向量检索。

## ADR-007：后台任务先用数据库队列

**决定**：首版通过 `processing_jobs` 表、锁和独立 Worker 承载任务，不立刻引入 Redis。

**原因**：减少个人部署组件，任务量有限且需要持久、可审计状态。

**重新评估条件**：任务吞吐、定时调度或多 Worker 竞争使数据库队列维护成本明显增加。

## ADR-008：模型 Provider 可替换

**决定**：解析理解、分类、Embedding、Rerank 和回答使用独立任务接口，不在领域代码中绑定具体供应商。

**原因**：支持云模型、本地 Ollama、隐私需求和成本优化，并允许不同任务选用不同模型。

## ADR-009：首版单用户但不写死用户边界

**决定**：UI 只支持一个用户；核心数据表预留 `owner_id` 或 `workspace_id`，但不实现团队权限矩阵。

**原因**：避免首版权限系统拖慢交付，同时保留以后迁移空间。

## ADR-010：知识图谱不是首版基础依赖

**决定**：首版仅保存实体提取结果和必要关系，不运行全量 GraphRAG。

**原因**：普通个人资料的主要问题是可靠采集、分类和召回；全量图谱成本高且在语料尚小时收益不确定。

**重新评估条件**：出现大量跨文档实体关系问题，且黄金评测证明混合检索无法满足。

## ADR-011：M3 检索先做 FTS 与结构切片，向量召回延后

**决定**：M3 第一小版只交付 PostgreSQL 全文索引（`tsvector` + GIN）以及
基于 `structured_content` 的父子切片；embedding、向量召回、RRF 融合和带
引用问答保留到 M3 后续。

**原因**：在拥有 50 份以内个人资料时，关键词 + 标题 + heading_path 路径
检索已经能命中绝大多数真实问题；过早引入向量会同时拖慢里程碑验收和
增加外部依赖（模型服务、pgvector 资源占用）。让 FTS 先稳定后再叠加
向量，有利于按 ADR-006 的“混合检索”策略分阶段做评测。

**重新评估条件**：M3 黄金集上 FTS Top 5 命中率低于 80%，或资料数 / 跨
文档问题显著上升，导致关键词召回不足。

## ADR-012：M3-2 问答只做单轮 FTS 检索，不引入向量与对话记忆

**决定**：M3-2 在不破坏 ADR-011 的前提下交付首版单轮带引用问答：
证据来自 `document_chunks` 的 PostgreSQL FTS 与 SQLite `LIKE` 召回；
模型输出受 `AnswerResult` 与 `validate_against_evidence` 严格约束；
不保存会话历史、不引入 embedding、不做 RRF。

**原因**：个人知识库首版必须能用自然语言提问并拿到可验证的引用，
但黄金评测集尚未建立，向量召回会同时拉高复杂度与外部依赖。在
FTS 之上先稳定“提问-召回-回答-引用”闭环，能更快暴露真实的问答
质量问题（截断、片段过长、引用造假、证据不足），再决定向量与
多轮的优先级。

**重新评估条件**：M3 黄金集上 FTS Top 5 命中率低于 80%、跨文档
问题占比明显上升、且问答错误主要由召回能力不足（而非生成或
引用校验）造成；同时 ADR-011 的重新评估条件也被触发。
