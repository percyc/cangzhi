# ADR-028：数据库快照新鲜度与查询一致性

状态：已接受（2026-09-22）

## 背景

PostgreSQL/MySQL 来源导入后由本地 Parquet/DuckDB 提供精确查询。这个边界保证了
回答可复现、远端数据库只读且不会被自然语言问答持续施压，但如果用户长期不重新导入，
快照可能已经落后于来源库。知识探索需要看见数据时间，并能按用户选择刷新，而不是把
旧数据伪装成实时数据。

## 决定

1. 数据库表仍先导入为版本化本地快照。快速问答、深度分析、REST 和 MCP 不把每次
   自然语言问题翻译成远端 SQL，也不在一次回答中混用刷新前后的版本。
2. 每个数据库来源提供三种简单策略：
   - `background`（默认）：达到间隔后，本次查询继续使用并标明旧快照，同时创建去重的
     后台刷新任务；
   - `strict`：达到间隔后拒绝数据集执行，立即创建刷新任务，客户端稍后重新发现数据集；
   - `manual`：只在管理员主动重新导入时刷新，过期查询明确警告。
3. 默认间隔为 24 小时，可配置 5 分钟到 30 天。时间阈值表示“需要刷新”，不表示来源
   数据一定发生了变化。
4. 数据集目录、Schema 和查询响应返回 `source_freshness`，包括快照时间、年龄、策略、
   阈值、是否过期、是否已有刷新任务和最近错误。MCP 复用同一服务响应。
5. 刷新使用数据库任务队列、幂等键和指数退避。新版本完成并提交后才替换当前快照；
   失败保留旧文档版本、数据集和 Parquet，不牺牲可恢复性。
6. `document_version_id`、`artifact_version` 和来源行继续绑定本次回答的事实版本。后台
   刷新不能让已经返回的证据悄然指向新数据。

## 原因

对每个问题实时访问业务库会把问答延迟、来源可用性和权限风险带进核心检索链路，也使
引用无法复现。版本化快照加显式新鲜度既保持藏知“可验证知识快照”的定位，又让对时效
敏感的场景能选择严格策略。三档策略比定时任务、Cron 和查询缓存等多个高级开关更适合
个人使用。

## 局限与后续

- 当前仍是整表/视图刷新，单表最多 10 万行；不是 CDC 或增量同步。
- 后台刷新由 Worker 消费任务，Worker 停止时会显示待刷新但不会自动完成。
- 来源库不可用时严格模式会继续拒绝过期查询；管理员可修复连接或临时改为后台/手动。
- 后续如需要分钟级实时分析，应新增经过审批的实时查询模式及独立资源/权限边界，不能
  把现有受控数据集查询直接改成任意远端 SQL。
