# 处理可靠性：运行统计、并发治理与故障恢复

日期：2026-10-22。更新：2026-10-23。第一批已在 v1.3.8 发布；第二、三批
收敛为 v1.4.0 的共享模型准入与串行监督执行。实际测试/部署见 PROJECT_STATUS。
下文保留规划动机和后续方向；本次精确边界以 ADR-034/035 为准：不含 RPM/TPM、
永久暂停 UI、自动探测或 CPU 并行，不自动重跑历史任务。

目标：批量入库时资源有上限、日常搜索问答可用、失败不长期占用执行容量，
且页面能区分排队、实际执行、退避和采集失败。原文、已有索引及历史失败记录不自动改写。
关联：CZ-S03、CZ-O06、CZ-Q05、CZ-Q09；发布规则见 [VERSIONING](VERSIONING.md)。

## 1. 改造前已核实的基线

- 当前普通Worker按阶段公平轮转、逐个领取并串行执行；每轮最多10次尝试不是10并发。
  普通`processing_jobs`有重试时间和执行时间，尚无统一心跳、执行租约与尝试身份。
- 对话Provider、查询向量、后台向量及外部OCR调用分散；请求超时和局部降级存在，
  但尚无API/Worker跨进程共享的渠道并发额度。深度问答部分同步请求在线程中执行。
- 知识增强已有自己的尝试ID/租约，WebDAV扫描已有持久租约；应复用其安全原则，
  不能将这些局部能力描述为普通任务已经具备崩溃恢复。
- 本轮只读核验的运行实例中，容量/队列快照成功，知识规模没有成功快照但有失败尝试。
  线上仍使用旧有效向量聚合；本地优化已验证但未部署。没有证据说明整个Worker停止。
- 当前知识规模一次执行多条聚合，任意一条失败会丢弃本组本次结果。页面只凭
  `sampled_at`为空就显示“等待后台首次采集”，导致已尝试失败与从未尝试混淆。

## 2. 第一批：统计恢复与WebDAV交付收尾

### 2.1 修复查询，不增加统计负担

纳入已开发的有效向量聚合FILTER优化，保持统计口径、每SQL2500ms、锁等待200ms、
低频采集和独立单连接不变。上一轮现场只读单次观察约203ms，并有5万向量隔离回归；
这不是P95或所有规模保证。仍超限时应优化查询/增量快照，不默认放宽超时或扫描正文。

### 2.2 指标级隔离与真实时间

- 在原三类快照下扩展指标元信息：值、最后成功时间、最后尝试时间、脱敏错误码、
  连续失败次数、预计下次尝试时间。扩展保留原data字段，旧快照可以只读映射为旧状态。
  具体存储字段及迁移在实施ADR中确定，不预先宣称无需迁移。
- 每条指标独立保存点，单项SQL失败后恢复事务，其他指标在剩余总预算内继续采集。
  保留失败项旧值及旧时间；从未成功为null，不填0，不把一项成功伪装成整组更新。
- 轮次预算按实际剩余时间收紧后续SQL，不通过“每项都能执行2500ms”突破总体预算；
  没有获得预算的指标标记未尝试，不算采集失败。历史趋势不得将旧值写成新测量。
- 失败重试采用有上限的退避及错峰；跨进程互斥与持久到期时间避免重启/多实例重试风暴。
  首次失败可比正常15分钟周期更早尝试，但必须有最小间隔及总负载上限。

### 2.3 页面状态与诊断

| 实际情况 | 页面应显示 |
| --- | --- |
| 从未尝试 | 尚未采集，等待后台执行 |
| 已尝试、首次失败 | 首次采集失败：具体指标及安全错误类型；尚无可用结果 |
| 部分指标成功 | 部分统计可用；失败指标显示未知/带时间的旧值 |
| 曾成功、本次失败 | 最近成功时间、失败项及预计重试时间；明确旧值 |
| 长期没有尝试记录 | 长时间未收到采集记录，建议检查Worker；不直接断言宕机 |

“重新读取快照”仍只读。首批不增加网页直接运行重聚合的按钮，避免反复点击冲击数据库。
后续若增加“请求重新采集”，只能提交受冷却、去重和后台资源上限约束的任务。
日志记录指标标识、错误分类、耗时，不记录原始SQL异常、连接信息或文档内容。

验收：首次成功、首次失败、有旧值失败、部分失败、数据库锁冲突、过期、恢复均有测试；
单项失败不隐藏其他成功计数，刷新页面不触发采集；部署后等待真实自动采集验证。
WebDAV既有未发布优化可在这一稳定性节点一并交付，保持其下载与解析状态区分。

## 3. 第二批：统一模型调用准入

### 3.1 两层容量与渠道共用额度

任务执行容量控制CPU/内存，模型调用容量控制外部请求，两者不是同一个计数器。
本地解析、转换/本地OCR、对话、Embedding、外部OCR分开约束；同版本会相互覆盖的
解析/重切/产物替换不能因为有空槽位就并行执行。不同任务不得共享SQLAlchemy Session。

API与Worker通过统一服务和PostgreSQL短事务协调。使用不含秘密的额度池ID，
渠道/账号配额共享时绑定同一池；必要时再加模型子限额。空间、Profile、调用用途只是
归属信息，不能各自复制一份渠道额度。外部OCR与对话使用同一上游配额时也要合并约束。
模型测试、摘要分类、增强、深度规划/回答、查询向量和后台向量均必须经过该层。

先提供保守默认值作为起点，而非吞吐承诺：本地重解析/转换各最多1，
独立对话池总并发2、后台最多1；独立向量池总并发2、后台最多1；独立外部OCR池最多1。
如果这些功能共享一个池，仍受共同总上限约束，不能相加。
前台保留容量、排队有上限；渠道仅支持1并发时采用有界等待和公平轮转，不伪称可以预留。
新资料优先但历史任务有保底机会；先完成安全控制再扩大Worker任务并行。

### 3.2 名额跟随真实请求

- 只在真正准备发送请求时获取模型名额，完成或失败后释放；检索、拼接、写库和
  深度探索的工具执行不占模型名额。拿不到容量不是任务执行失败，不消耗模型重试次数。
- 多资源按固定顺序申请；无法获得时有界等待或释放已取得资源、重新排队，避免死锁。
  等待模型容量和退避时不占网络调用槽位，也不长期持有数据库连接/行锁。
- 使用统一上下文保证正常/异常清理；取消必须关闭请求并确认本地执行已退出。
  外层等待取消不等于线程中的同步HTTP停止，不能在它仍运行时过早发放名额。
- 优先使用可取消异步传输；无法及时中断的解析/转换工作放入可终止的受控子进程。
  同时限制连接/读写空闲超时与请求/任务总期限，避免慢速响应无限续命。
- 跨进程槽位采用租约和唯一持有者，续租/释放都校验持有者；租约失效后拒绝旧尝试
  发布结果。失去协调库时暂停新外发，不绕过并发限制；不能确认旧执行结束时保守隔离。
  断网或取消不能保证上游立即停止计算/计费，不承诺跨供应商“恰好调用一次”。

### 3.3 频率、重试和渠道冷却

并发限制不等于RPM/TPM限制；渠道配额明确时增加频率/Token预算约束，未配置时不能
声称已满足上游全部限额。429参考Retry-After，网络/临时5xx采用退避加随机错峰；
401/403、模型不存在等暂停相关渠道并要求修正，而不是每个文档重复尝试。
非法输出、内容限制、确定性文件错误分开记录。连续失败触发有限冷却和少量恢复探测。
重试只有一层负责，避免HTTP库重试与任务重试相乘；付费增强继续遵守显式调用预算，
结果未知的调用计入已尝试，不能自动退还预算并无限重发。

验收：多个API/Worker进程合计不超过池上限；429/5xx/无效输出/取消均释放真实调用槽位；
等待/退避不占模型名额，同渠道不同模型/空间不能绕过；后台积压下前台仍能获得容量。

## 4. 第三批：普通任务租约、恢复和可观测性

- 普通任务增加worker身份、attempt_id、心跳、lease_until及硬截止时间。
  短事务领取任务，按实际执行容量领取，不预先把整批记录标成processing。
- 心跳不无限延长硬截止时间；超时需停止执行再释放容量。崩溃通过到期租约恢复，
  恢复次数有限，幂等写入和尝试身份检查同时防止重复产物与迟到覆盖。
- 结果发布核对文档版本、内容哈希、配置/Profile及当前尝试；仅将最终赋值加锁
  不足以保护外部产物，临时文件与数据库提交也必须按尝试隔离。
- 扩展现有公平调度，先保障同文档安全，再增加不同文档/阶段的有界并行；不并行
  执行当前不具备原子版本替换的同版本重切流程，不借此恢复全部旧任务。
- 普通Worker和维护执行器共享所有权协议；旧无租约processing不能直接当作过期
  新任务接管。升级须安排执行器切换，历史孤儿由维护者明确确认，防止新旧Worker双执行。
- 页面区分等待执行容量、等待模型额度、执行中、退避、暂停待修复和最终失败。
  运行概览展示额度占用/上限、等待量、超时与恢复数；采集线程心跳不能冒充任务心跳。
  名额释放与任务状态落库是两件事：落库失败可导致状态滞留，应通过租约修复，不能
  为了维持一个processing状态永久保留调用名额。

验收：多进程争抢、强制终止、重启、数据库暂不可用、失联后恢复、旧响应迟到、
重试上限和版本更新均有集成测试；事实源与已有可用索引不变，无无限重试或重复提交。

## 5. 实施与发布边界

先完成第一批统计修正，再实施第二批共享准入，最后按第三批安全条件扩展任务并行。
第二、三批设计有依赖：槽位租约与普通任务租约要统一所有权语义，不能只加线程池。
编码前补ADR、迁移与兼容/回退方案；不更改公共REST/MCP知识范围契约。

- 第一批可作为下一补丁节点，拟`v1.3.8`，以发布时远端标签核对为准。
- 第二、三批形成可完整验收的并发/恢复能力后，再评估次版本，拟`v1.4.0`。
- 以上是规划，不立即创建标签、调整VERSION、推送或部署；未验收能力不能进入正式标签。
- 重要节点必须执行[发布检查清单](VERSIONING.md#发布检查清单)，记录源码提交、测试、
  部署验证范围、标签及各远端结果。部署仍按仓库约定由维护者执行或另行明确授权。
