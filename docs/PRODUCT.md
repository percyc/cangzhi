# 藏知产品定位

本文定义藏知解决的问题、产品边界和长期方向。具体实现见
[技术架构](ARCHITECTURE.md)，交付顺序见[路线图](ROADMAP.md)。

## 1. 一句话定位

**藏知是个人可控的 AI 知识中枢：把分散内容持续沉淀为可追溯、可检索、可被人和智能体复用的长期知识资产。**

品牌短句是：**藏有所知，问有所据。**

它不只是笔记软件，也不只是“上传文件后聊天”的 RAG 页面。藏知管理的是知识从
进入、保存、理解、组织、索引、取证到再次利用的完整生命周期。

首要用户是有长期研究、工作和阅读积累的个人。首个部署形态保持单用户、自托管；
团队空间、复杂权限和协同审批不是当前目标。

## 2. 解决的问题

### 2.1 收集入口分散，整理成本高

网页、文件、临时想法和网盘目录分布在不同工具中。传统知识库往往要求用户在保存
时先选择目录、填写标签和设计规则，最后因为维护成本过高而停止整理。

藏知提供统一入口，先可靠保存，再异步解析和整理。高置信度结果自动落库，只有失败
或低置信度内容进入收件箱，不让“如何分类”阻断采集。

### 2.2 保存了文件，不等于形成了知识

文件夹只保存对象，不能稳定回答“这份资料讲了什么、属于什么主题、与哪些内容
有关”。简单把全文转成向量，同样会丢失章节、条款、页码和上下文。

藏知保留原文和版本，以结构树为中间表示，再完成文档类型识别、摘要、分类、标签、
父子切片和索引。AI 负责理解与建议，确定性规则负责边界、安全和可重建性。

### 2.3 单一向量检索不适合所有问题

精确名称、法律条款、数字和代码适合关键词检索；概念相近但措辞不同的问题适合向量
检索；来源、分类和标签又属于结构化过滤。只使用其中一路，都会在某些场景明显失效。

藏知默认采用全文与向量双路召回、元数据过滤和 RRF 融合。向量服务不可用时自动
降级到关键词检索，不让外部模型故障使知识失去可用性。

### 2.4 AI 回答容易脱离原文

普通聊天界面很难区分模型常识、推断和知识库证据，长文切片还可能在错误边界上截断
语义。

藏知要求答案引用具体文档版本和片段，并保留章节、页码、段落和原文位置。证据不足
时不调用模型或明确说明不足；任何摘要、分类、切片和向量都可以从事实源重新生成。

### 2.5 知识被锁在某个页面或某个模型里

个人知识不应只能由藏知自己的问答页使用，也不应绑定某一家模型、向量渠道或 Agent
平台。

藏知通过网页、稳定 REST API、CLI、MCP 和 Skill 暴露同一套知识范围、检索与引用
能力。Hermes、OpenClaw 等外部智能体默认从藏知取证，再用自己的模型完成推理，
避免重复调用模型。

### 2.6 外部来源变化与本地知识生命周期脱节

网盘文件可能被改名、更新或删除。简单同步会造成重复导入、静默丢失，甚至误删本地
知识；删除连接器、删除知识和远端删除也常被混为一件事。

藏知把“连接器、远端文件、已入库知识”分开管理。WebDAV 始终只读；远端缺失经过
连续成功扫描和保护期后才确认，默认只把知识移入回收站，远端恢复时自动恢复，也可
明确保留为本地快照。

### 2.7 长期使用需要数据主权

知识库的生命周期通常比某个模型和应用版本更长。用户需要能下载原文、导出可读内容、
备份数据库，并在索引损坏或更换模型后重建。

藏知把原文、版本和结构化元数据视为事实源；向量和其他索引是可替换的派生数据。
系统支持原文下载、Markdown/JSON 导出、全库导出和数据库加文件存储备份。

### 2.8 可阅读知识和可计算知识需要不同引擎

文章、PDF 和笔记以章节、段落和语义片段为基本单位；Excel、CSV 等二维资料则以
数据集、字段、行和确定性计算为基本单位。把表格全部文本化后交给向量检索，不能
可靠完成计数、筛选、求和和分组，也会产生大量同构向量。

藏知在产品层保持统一知识入口，在内部采用文档引擎和数据集引擎双轨。工作簿仍是
可分类、打标签、版本化和追溯的知识对象，其中每个可查询区域形成数据集。向量负责
发现相关数据集和字段，受限查询引擎负责全量事实计算；结果引用工作表、条件和原始
行范围。藏知支持知识型数据集问答，但不以替代 Excel、BI 或数据仓库为目标。

## 3. 核心闭环

```text
采集 → 保真保存 → 解析理解 → 自动组织 → 建立索引
  ↑                                      ↓
纠正 ← 追溯引用 ← 搜索/问答/Agent 取证 ← 复用
```

1. **采集**：链接、上传文件、随手记和外部只读目录进入统一处理管线。
2. **保存**：先创建记录并保存原文或快照，AI 失败不影响资料留存。
3. **理解**：提取结构，识别类型，生成摘要、分类和标签。
4. **组织**：默认分类树提供低成本起点，分类、标签和知识范围可继续调整。
5. **索引**：文档建立结构优先父子切片；数据集保留全量行索引，只建立少量目录切片和代表性向量。
6. **取证**：搜索、问答、API、CLI 和 MCP 使用同一检索与范围语义。
7. **追溯**：结果和回答定位到具体文档版本与原文片段。
8. **纠正**：用户可修改分类、标签和处理结果，未来用于偏好学习和质量评测。

## 4. 产品能力分层

### 4.1 事实源层

- 原文件、网页快照和随手记原始内容
- 文档版本、来源身份和处理记录
- 回收站、永久删除、导出与备份
- WebDAV 等外部来源的只读生命周期

### 4.2 理解与组织层

- 确定性文档类型识别
- AI 摘要、分类和标签
- 默认分类树与用户自定义分类
- 收件箱、失败重试和人工纠正

### 4.3 检索与证据层

- 结构优先父子切片
- PostgreSQL 全文检索与 pgvector
- 元数据过滤、RRF 融合与故障降级
- 文档版本、章节、页码、段落和 source span 引用

### 4.4 使用与接入层

- 知识库浏览和精确搜索
- 有引用的知识问答与知识范围
- REST v1、CLI、MCP 和通用 Skill
- 独立、最小权限且可撤销的访问令牌

## 5. AI 在系统中的位置

AI 是增强能力，不是数据可靠性的前提。

- 不配置模型时，采集、原文保存、基础解析、全文检索和人工组织仍然可用。
- 对话模型用于摘要、分类、标签、整理和带引用回答。
- Embedding 模型独立配置；新索引构建完成前，旧索引继续服务。
- 更换渠道、密钥或模型时先测试兼容性，再决定复用、重建或切换索引。
- 提示词和处理版本用于追溯，不要求普通用户在日常流程中配置。
- 大模型不能静默覆盖原文，也不能决定永久删除。

## 6. 交互与信息架构

- **收件箱**：处理中、失败、待整理及需要关注的资料。
- **知识库**：浏览、筛选和批量管理已经沉淀的知识。
- **搜索**：面向“找资料”，强调筛选、命中片段和来源定位。
- **问知识库**：面向“基于证据回答”，使用会话式交互并选择知识范围。
- **分类与标签**：维护组织体系，AI 可以提供合并和归类建议。
- **设置**：按对话模型、向量与索引、知识源、数据与备份、外部接入分区。

搜索与问答共享检索底座，但服务不同意图，因此保留两个入口；知识库中的快捷动作
只负责把当前范围带入对应入口，不复制另一套搜索或问答页面。

问答页面采用聊天式呈现并把问题、回答、范围和实际引用保存到云端，目的是跨设备
回看、复核和重跑，而不是建立第二套个人记忆。默认每次提问都是独立任务，模型不会
自动读取此前问答；需要连续推理和长期个性化记忆时，由 Hermes、OpenClaw 等专门
Agent 使用藏知的检索、MCP 或 Skill 取证。

## 7. 设计原则

1. **低打扰**：先保存，后处理；默认自动完成，异常集中处理。
2. **原文优先**：原文和版本是事实源，AI 产物必须可追溯、可重建。
3. **结构优先**：优先尊重章节、条款、段落和表格边界，再使用 token 限制兜底。
4. **混合检索**：不把向量相似度当作唯一相关性。
5. **证据约束**：知识问答必须基于检索证据并提供可核验引用。
6. **渐进配置**：普通用户不需要配置切片规则和提示词；高级能力按需展开。
7. **可替换**：对话模型、向量模型、存储和接入平台都不能成为知识锁定点。
8. **安全可逆**：删除先进入回收站；外部来源只读；不可逆操作必须明确发起。
9. **同一能力，多种入口**：网页、API、CLI 和 MCP 复用相同服务与权限语义。

## 8. 当前边界

当前版本面向个人部署，重点是把知识可靠沉淀并开放给个人 Agent 生态。以下能力暂不
作为基础依赖：

- 多用户、组织空间、复杂角色和协同审批
- 自动替用户永久删除或覆盖原始内容
- 以完整知识图谱替代基础检索
- 让智能体默认拥有写入和管理权限
- 用更大的回答模型掩盖召回质量问题
- 把藏知扩展成通用网盘或双向文件同步工具

## 9. 成功标准

北极星目标：

> 用户保存资料时无需额外整理，数周或数月后仍能准确找到、核对出处，并能在其他
> AI 工具中安全复用。

持续评估四类指标：

- **沉淀可靠性**：原文保存成功率、解析成功率、失败可恢复率。
- **整理成本**：需要人工重新分类和处理的比例、每周整理耗时。
- **检索质量**：黄金问题 Top 5 证据命中率、过滤准确率、降级可用性。
- **回答可信度**：引用覆盖率、无依据陈述率、引用定位成功率。

个人 Beta 的目标不是功能数量，而是用真实资料长期运行后，仍然保持低维护、可解释
和可迁移。
